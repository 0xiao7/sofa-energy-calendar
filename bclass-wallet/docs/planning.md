# Part A — 產品規劃書

## 1. 專案定位

- **專案名稱（暫定）**：B.CLASS Wallet
- **副標**：人生不是只有餘額，而是現金流節奏。
- 本系統並非傳統「記帳 APP」，而是**人生現金流導航系統**。

核心目標：

- 協助使用者掌握財務節奏
- 預測未來壓力
- 管理負債與到期日
- 分析人生事件與金流關聯
- 建立長期生存能力

## 2. 產品核心差異化

| 傳統記帳 APP | B.CLASS Wallet |
| --- | --- |
| 著重分類 | 著重「時間軸」 |
| 著重統計 | 著重「生存節奏」 |
| 偏會計思維 | 著重「人生壓力」 |
| 使用壓力高 | 著重「現金流未來預測」 |

## 3. 核心 UI 架構

### Layer 1｜Calendar Dashboard（主畫面）
以「大面積月曆」為核心。每個日期格顯示：收入、支出、到期日、負債提醒、現金流危險度。

**顏色狀態系統**

| 顏色 | 狀態 |
| --- | --- |
| 綠色 | 安全 |
| 黃色 | 注意 |
| 橘色 | 緊繃 |
| 紅色 | 危險 |
| 黑色 | 現金流斷裂 |

### Layer 2｜Daily Detail（日詳細）
點擊日期進入，顯示：

- **今日摘要**：今日收入、支出、結餘、現金流狀態
- **支出細節**：早餐、房租、卡費、車貸、信貸、娛樂、副業收入…
- **AI 建議**：例如「本週支出過高／建議降低娛樂支出／近期負債壓力增加」

### Layer 3｜Financial Report（報表系統）
- **月總結**：總收入、總支出、淨現金流、負債變化、投資變化、支出分類比例
- **年總結**：年收入、年支出、年資產變化、最危險月份、最佳月份、副業成長
- **自訂區間分析**：自由選日期範圍 / 特殊事件期間（考試、轉職）生成報表

## 4. 負債管理系統

- **Debt Dashboard**：信用卡 / 信貸 / 車貸 / BNPL / 人情借款，顯示剩餘金額
- **到期日管理**：還款提醒、延遲警告、現金流危險提示
- **AI 還款策略**：雪球法（先清小額）／雪崩法（先清高利率）

## 5. AI 生存導航系統

- **現金流預測**：例「6/23 後可能進入危險現金流」
- **生存天數計算**：例「目前可維持 42 天」
- **壓力分析**：情緒性消費增加、深夜外送增加、娛樂支出偏高
- **副業建議**：依技能 / 證照 / 收入結構，推薦可變現方向、接案模式、長期收入路徑

## 6. 技能與人生模組（B.CLASS 整合）

未來整合：職能樹、國考系統、技能變現、第二人生導航。
使用者輸入（記帳士 / Excel / AI 工具 / 法規能力）→ 系統推薦可接案、可兼職、適合副業方向。

## 7. MVP（第一版）v0.1 範圍

**必做**：Calendar Dashboard、Daily Detail、收支記錄、負債管理、到期提醒、月報表、AI 簡易分析。

**暫不開發**：股票串接、銀行 API、自動報稅、加密貨幣、自動分類 AI。

## 8. 技術架構

- **Frontend**：Flutter（iOS / Android 共用、UI 動畫強、行事曆套件成熟）
- **Backend**：Supabase（Auth / Database / API / Realtime / Push Notification）
- **AI Engine**：Gemini API / OpenAI API（財務分析、生存預測、副業建議、消費分析）

## 9. Database 規劃

`users`、`wallets`、`transactions`、`debts`、`subscriptions`、`income_sources`、`skills`、`licenses`、`cashflow_predictions`、`life_events`、`ai_analysis_logs`。
（實作見 [`../data/schema.sql`](../data/schema.sql)）

## 10. 商業模式（初步）

- **免費版**：基本記帳、月曆、報表
- **Pro 版**：AI 分析、生存預測、長期趨勢、技能導航、B.CLASS 模組

## 11. 產品核心精神
B.CLASS Wallet 不是理財 APP，而是「人生節奏導航系統」，讓使用者看懂自己的時間、壓力、現金流與未來方向。

# Part B — 規劃評析與建議

> 以下是針對這份規劃書的補充分析：**現有市場差異化、可升級／補強的部分、風險、以及 MVP 落地的優先順序**。

## B1. 一句話定位檢驗

這份規劃最強的點是 **「把記帳的時間軸從『過去』翻轉成『未來』」**。
傳統 App 回答「我上個月花了多少」；B.CLASS 想回答「**我還能撐幾天、哪一天會出事**」。這個敘事（生存導航）是真正的差異化，要當成北極星，所有功能都該服務它。

> 建議：MVP 的成功指標不是「記了幾筆帳」，而是「使用者打開 App 時，第一眼是否看懂自己未來 60 天的紅綠燈」。

## B2. 現有市場差異化（競品定位）

| 類別 | 代表 | 核心邏輯 | B.CLASS 的切入點 |
| --- | --- | --- | --- |
| 自動記帳 | 麻布記帳、CWMoney、Moze | 連結帳戶/發票，自動分類，**回顧過去** | 不做自動連結，改做**未來預測**，主打「先知道會不會出事」 |
| 預算管理 | YNAB、MoneyMoney | 信封預算法、零基預算 | 預算偏「分配」，B.CLASS 偏「**時間軸上的存活**」，更貼近月光族/負債族 |
| 負債管理 | Debt Payoff Planner、Undebt.it | 雪球/雪崩試算 | 把負債到期日**畫進同一張月曆**，與現金流危險度連動 |
| 訂閱管理 | Rocket Money | 抓固定支出 | 訂閱只是其中一個「未來到期事件」來源 |

**差異化護城河（建議聚焦這 3 點）**：
1. **一張月曆看未來**：收入、支出、到期日、危險度全部疊在同一個時間軸 → 別人沒有把「未來現金流」視覺化成紅綠燈月曆。
2. **生存天數 / 斷裂日**：把抽象焦慮變成「42 天」「6/23」這種可行動的數字。
3. **人生事件 × 金流**：考試期、轉職空窗期的區間分析 → 連結 B.CLASS 的人生導航敘事，這是別人做不出來的品牌資產。

## B3. 可升級／補強的部分（規劃缺口）

原規劃較完整，但有幾個**會直接影響「預測準不準」**的關鍵點沒寫清楚，建議補上：

1. **預測的資料來源**：要能預測未來，必須有「**未來會發生的事**」。原規劃的 `transactions` 都是已發生的。
   → **強烈建議新增「重複規則 / 預期收支」**：薪資預計幾號入帳、房租幾號扣、信貸每月還多少。沒有這層，所謂「現金流預測」其實算不出來。（已在 `schema.sql` 用 `income_sources.is_recurring`、`subscriptions.cycle`、`debts.due_day` 預留。）
2. **危險度的定義要可計算**：五色燈不能只是感覺。建議用明確公式：
   - 逐日推算「預估餘額」= 期初餘額 + 區間內預期收入 − 預期支出 − 當日到期負債/訂閱。
   - 對照 `safety_buffer`（安全水位）切五級：`>buffer 綠`、`buffer~50% 黃`、`50%~25% 橘`、`>0~25% 紅`、`<0 黑`。
   - （本 repo 的 MVP 原型已實作此公式，可直接沿用。）
3. **金額用整數（分）存**：避免浮點誤差，報表才不會差一塊錢。（schema 已採 bigint。）
4. **多帳戶 / 多錢包**：規劃只寫 `wallets` 但 UI 沒提。生存導航需要「總可動用現金」，建議首頁可切「全部錢包合計」。
5. **AI 的成本與隱私**：每次都打 Gemini/OpenAI 會貴且慢。建議：
   - **規則引擎先行**（survival days、斷裂日、雪球/雪崩）→ 不需 LLM，免費版即可給。
   - LLM 只用在「**自然語言洞察與副業建議**」（Pro 版），且傳給模型前先做數據去識別化。
6. **通知策略**：Push 是這類 App 的命脈（到期前 3 天、進入紅色當天）。建議列為 MVP 後段必做，而非「未來」。
7. **資料可攜 / 匯出**：理財資料使用者要能帶走（CSV 匯出），降低使用門檻與信任成本。

## B4. 風險與務實提醒

- **冷啟動的記帳惰性**：所有記帳 App 的死因都是「懶得記」。B.CLASS 的解法應該是 **「固定支出自動帶入」**——使用者只設定一次房租/貸款/訂閱，月曆就能自動長出未來。手動記帳只補變動支出（餐飲、娛樂）。這點要當成留存的核心設計，不是附屬功能。
- **「壓力分析」要小心定位**：偵測「深夜外送增加、情緒性消費」很有記憶點，但要避免變成說教或道德審判。語氣建議走「**陪伴 / 教練**」而非「警察」。（這點與本 repo 既有專案的「自我覺察、非評判」精神一致。）
- **不要過早做技能/國考模組**：B6 的人生模組很迷人，但會稀釋 MVP 焦點。先把「現金流月曆」做到讓人離不開，再談第二人生。

## B5. 落地優先順序（建議的 MVP 切法）

把原本的「v0.1 必做」再切成三個可交付的里程碑，**每個里程碑都能單獨上線驗證**：

**Milestone 1 — 看得到未來（最小可用）**
- 月曆 Dashboard（五色燈）＋ 收支手動記錄 ＋ 期初餘額設定
- 逐日餘額推算 ＋ 生存天數 ＋ 斷裂日
- ✅ *本 repo 的 `index.html` 原型已涵蓋此里程碑，可離線試玩驗證敘事。*

**Milestone 2 — 自動長出未來（留存關鍵）**
- 固定收入 / 訂閱 / 負債的「重複規則」→ 自動把未來收支畫進月曆
- 到期日提醒（Push）、Daily Detail、月報表

**Milestone 3 — 智慧層（差異化 / Pro）**
- 規則型還款策略（雪球/雪崩試算）
- LLM 洞察（消費型態、壓力分析、副業建議）
- 區間 / 人生事件分析

**技術建議**：Flutter + Supabase 的選型合理。但**驗證「敘事是否打中人」不需要先寫 Flutter**——可先用本 repo 的純前端 HTML 原型（localStorage）找 10 個目標使用者測，確認「五色燈月曆 + 生存天數」真的有感，再投入 App 開發，省下大量成本。

## B6. 給 Claude Code / 未來協作者的技術脈絡

- MVP 原型 [`../index.html`](../index.html)：純前端單檔、localStorage 持久化、離線可跑，**不需後端即可展示完整敘事**。風格刻意對齊本 repo 既有專案（單檔、離線、繁中）。
- 危險度公式、生存天數、雪球/雪崩排序皆為**純規則計算**，原型內已實作；正式版搬到後端只是把資料來源從 localStorage 換成 `schema.sql` 定義的表。
- 接 LLM 時，把原型算好的數據摘要當 context 餵給模型，請它「**只做自然語言洞察與建議**」，不要讓模型算數字（避免幻覺與成本）。
